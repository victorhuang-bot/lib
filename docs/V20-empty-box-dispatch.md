# MovingMatch V20 空箱調度：實作與驗收規格

狀態：開發分支規格草案。禁止在完成測試前部署正式環境或改寫既有簽收資料。

## 不可破壞的既有行為
- 司機頁面、司機 API 與四項公文／圖書數量欄位不變。
- 分館原有簽收與稍後補簽不變；有有效空箱調度時才附加確認欄位，與原簽名共用。
- 現有配送、簽名、歷史、QR、PIN、路線、停送、順延資料完整保留。
- 不以覆寫原有 note_final 儲存結構化調度資料；若要顯示於備註，使用衍生顯示內容。

## 分館盤點
- 欄位：未使用空箱、已裝書用箱、損壞箱、持有總箱數（前三者加總）。
- 每次盤點記錄 branch_id、數量、盤點人、盤點時間、備註、版本；僅分館本人可寫入。
- 盤點快照與庫存異動分開，保留歷史與稽核。

## 分館需求
- 分館自行提出補箱申請，數量為正整數，可查看剩餘未補足量。
- 「缺空箱分館」只按有效且未補足申請計數，不根據最低庫存推論。
- 完成／取消申請不列缺箱；部分補足仍列缺箱。

## 總館／秘書室看板
- 已盤點分館：可點擊列出館名、盤點日期時間與各項數量。
- 未使用空箱：已盤點分館最新未使用數量加總，顯示資料涵蓋率。
- 缺空箱分館：點擊列出有效申請、未補足箱數與申請時間。
- 未盤點清單及提醒：僅提醒未盤點／逾期盤點館，保留提醒時間與操作人。

## 多來源調度
- 一筆調度需求館可有多個收取館；每個來源各自指定數量與預定收取日期。
- 需求館另有預定送達日期；系統依有效配送班表建議，總館可調整。
- 來源可調出量不可為負；須防止重複分配；異線或異日須記錄在途／倉庫暫存。
- 停送／颱風順延需標記待重新安排，不得默默完成調度。

## 交接與提前送達
- 司機不新增空箱頁面、按鈕或額外簽名。
- 只有存在該館有效待交接任務時，分館原簽收頁才顯示預定與實際交回／收到數量。
- 需求館可提前確認收到空箱，無須總館先修改預定日期；保留原預定日期。
- 實際交接日期與簽收時間分別儲存，稍後補簽不能將補簽日誤認為送達日。
- 當日沒有原圖書配送時，分館可從原首頁待交接區確認，不能建立假配送。
- 僅在交接確認後更新庫存；所有異動冪等、可稽核，超額及差異需原因。
- 一次簽名與稍後補簽沿用既有機制，不重複入帳。

## 建議獨立資料結構
- empty_box_stocktakes: 盤點快照
- empty_box_requests: 分館補箱申請與未補足量
- empty_box_transfers: 需求館、預定／實際送達、狀態
- empty_box_transfer_sources: 多收取館、各自數量、預定／實際收取日
- empty_box_handoffs: 各站實際交接、確認人、確認時間、原配送關聯（可為 NULL）
- empty_box_movements: 庫存流水帳、唯一業務事件鍵
- empty_box_reminders: 盤點提醒紀錄
所有新表須有 CHECK、FK、唯一性、交易安全與索引。SQLite/PostgreSQL 相容。

## 上線關卡
1. 在隔離資料庫執行 schema migration 並驗證可重跑。
2. API 權限測試：分館不可讀寫他館；總館／秘書室可調度；司機不新增權限。
3. 測試多來源、部分補足、提前送達、跨日補簽、重複請求、停送、跨路線、庫存一致性。
4. 手機與桌機畫面驗收，確認舊有圖書／公文簽收不變。
5. 備份正式資料庫，先執行非破壞性 migration，再部署程式，最後驗證 Render live 與實際流程。
