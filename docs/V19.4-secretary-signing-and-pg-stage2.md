# V19.4 總館簽核安全修復與 PostgreSQL 第二階段工具

本次僅修改本機程式並執行 SQLite、mock 與靜態檢查。未連接 PostgreSQL、未執行真實資料清理、未寄信、未推送或部署。第二階段資料庫結果全部為 **BLOCKED：等待執行與限定復原授權**，不能以本機測試代替 PostgreSQL 驗收。

## 總館簽核修復

原先路線簽核直接更新簽名與時間，日報最終簽核的 UPSERT 也會覆寫既有值；缺少已簽核／已鎖定的伺服器端防護，重送與並行請求可能取代歷史紀錄。

`app/main.py` 的 `secretary_route_sign()` 與 `final_sign()` 改為：

- 保留 SECRETARY 角色與原有完成配送、司機簽名、公文數量等前置條件。
- 讀取狀態、檢查日報鎖定、條件式寫入及稽核共用一個交易。PostgreSQL 使用現有交易級 advisory lock；SQLite 使用 BEGIN IMMEDIATE。
- 未鎖定的路線收到相同簽名重送時回傳成功與原始時間，不更新資料、不新增稽核、不發布重複事件；其他簽名回傳 409。
- 依路線實際 service_date 檢查鎖定。日報鎖定後，包括相同簽名，也拒絕路線重新簽核。
- UPDATE／UPSERT 本身再加入「尚無簽名／時間且未鎖定」條件，檢查 rowcount。既有不完整簽核紀錄同樣拒絕覆寫。
- 簽核與稽核一次提交；稽核失敗則整筆回滾。原始簽核人保留於既有 audit_logs，沒有新增帳號或歷史補填流程。

前端辨識 already_signed=true，顯示「此路線已完成簽核，原簽名及時間均已保留」；首次成功顯示「簽核完成」，HTTP 409 顯示拒絕原因。

沒有新增總館簽名更正入口；需要更正時，維持拒絕修改，另行審閱授權流程。日報最終簽核重送一律 409，保留原始鎖定資訊。

預設執行 runner 只輸出離線計畫。真實執行需要同時提供資料庫寫入與限定清理旗標，且必須先取得使用者授權；旗標不能取代授權。完整十項執行還要求本機瀏覽器、Node 22+ 與 CDP helper，缺少即在連線前 BLOCKED。

所有實體連線（包括觀察連線、隔離測試連線、pool 新建與替換連線）經 VerifiedConnection.connect，強制 verify-full 與系統 CA。驗證有效 host、dbname、sslmode、CA 設定、current_database/current_schema、PostgreSQL 18.6、pg_stat_ssl、backend PID，再交給業務程式使用。驗證失敗關閉連線並全域停止後續 SQL。pool 無法攔截即 BLOCKED；沒有正式 DSN 或通用 DATABASE_URL 回退路徑。

runner 不使用獨立子程序產生資料庫連線；並行 API 測試使用獨立 TestClient 與真正不同的 PostgreSQL backend，在實際業務鎖定前設 barrier，驗證不同 PID。瀏覽器子程序只呼叫 loopback API，資料庫連線仍由受驗證的應用程式 pool 建立。資料庫層雙程序初始化已屬第一階段；本 runner 的第二階段並行測試針對業務請求。

## 合成資料生命週期與失敗復原

每次執行使用 `V194_FUNC_<UUID>_T<case>`。每案例最多兩個使用者、兩個司機、兩條路線與受限數量的分館及業務資料；全部是合成身分、隨機驗證資訊與測試簽名。K13/K13S 是相容性案例必要的固定代碼，以帶識別碼的分館名稱及本次主鍵證明歸屬。

執行前必須符合 public 26 表、43 索引、唯一正確 Migration 版本、其他資料表全空、沒有額外使用者 Schema。已有資料一律 BLOCKED，不清空。全程持有驗收專用 advisory lease，避免兩份 runner 同時執行。

真實 API 會 commit，因此案例 1–9 的 fixture／業務流程需要提交，才能驗證獨立連線可見性與實際端點行為。不能用假 commit 代替。每次 DML 提交前，將不含驗證資訊的隨機收據持久登錄於權限 0600 的 JSON，包含交易與操作歷程。精確主鍵、完整行指紋與 HMAC 歸屬證據只留在記憶體，不持久保存 session token hash、密碼衍生值或完整行指紋。案例 2、3 的負向交易回滾；案例 10 的四種 K13/K13S 子情境使用 force_rollback。其他案例的已提交合成資料須經另行授權的限定復原器處理。

復原器在同一交易內鎖定受控資料表，重新驗證 run UUID、記憶體 HMAC、測試識別碼、關聯歸屬鏈、catalog、Migration、所有資料的主鍵與指紋後，才依相依順序逐筆執行「登錄主鍵 AND 完整行指紋」DELETE。未登錄、被外部修改、未決交易或提交結果不明時，不執行清理。rowcount 不符則整筆復原交易回滾。清理器不刪除 Migration、Email 紀錄，不執行 DROP／TRUNCATE／無條件 DELETE。提交並關閉可寫連線後，另建經驗證的獨立連線，在伺服器端 READ ONLY 交易比較完整資料、Schema、索引與 Migration 快照，業務資料應回到 0；無獨立證據不得回報 PASS。

程序中斷或 commit ACK 不明時保留不含憑證的收據清單並停止。精確證據刻意不落地，因此任何重新載入的清單皆 BLOCKED，不能授權自動刪除；後續必須另行審閱、唯讀盤點與取得人工復原授權。正常程序內且歸屬可證明時，才可使用事先取得的限定復原授權。本次沒有執行真實復原。
