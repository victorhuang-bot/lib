# V19.4 初始化安全修復

本次僅本機程式修復與離線測試。未連接外部資料庫、執行 Render Migration、寄送真實 Email、修改 Render 設定、修改 PR #26、推送、合併或部署。

## 行為變更

| 入口 | 修復後 |
| --- | --- |
| 匯入 `app.main` | 不建表、不建帳號、不產生配送、不執行重設 |
| FastAPI startup | 只以 SELECT 驗證必要資料表及欄位；不相容時停止啟動 |
| `init_db()` | 明確呼叫的 Schema-only 初始化及 Migration，不含業務資料種子 |
| `seed_demo_data()` | 明確呼叫；只允許 development/test、獨立 DATA_DIR 的空白 SQLite；正式模式與 PostgreSQL 一律拒絕 |
| `reset_test_day_once()` / `apply_demo_branch_limit()` | 所有模式一律拒絕，未提供破壞性重設介面 |
| 啟動時名冊／司機／K13 身分同步 | 不再自動執行；既有明確修復函式保留供審閱及個別操作 |
| `ensure_today()` / `rebuild_service_date()` | 正常業務入口只補缺漏；不更新或刪除既有配送及關聯紀錄；鎖定日報直接返回，已簽核路線不新增配送 |

總館／管理者 `/api/dashboard/today` 保留安全建立當日配送能力；預填、排程流程仍可明確建立配送。司機、分館、歷史補簽、更正、總館簽核、報表、QR/PIN 與即時事件 API 未移除。應由總館建立／管理當日配送；啟動本身不再偷偷補建。

## 原因及交易範圍

原本模組匯入即呼叫 `init_db()`，將 Schema、示範資料、正式名冊、當日配送及清除流程混在一起。一次性標記缺少時可清除既有簽收；每日重建也可能刪除被不完整條件判斷為未操作的配送。各 helper 自行 commit，使後續錯誤無法整批復原。

`app/schema.py` 抽出原有基礎 DDL，保留既有表名及欄位。SchemaTransaction 逐條執行固定 DDL，避免 SQLite executescript 的隱含提交；攔截舊 Migration helper 的 commit。執行器先互斥，再依既有順序執行 Migration、驗證必要欄位、記錄 `schema_migrations`，最後只提交一次。失敗 rollback，且呼叫端在 finally 關閉連線。

SQLite 使用 BEGIN IMMEDIATE；PostgreSQL 使用 transaction advisory lock，並將 Migration timeout 改為 LOCAL，避免連線池遺留 session lock／timeout。Schema 初始化不再執行 setval，也不包含正式名冊同步、司機設定更新或配送清除。明確的本機示範種子也在同一交易中完成，不保留部分種子。

## 明確初始化入口

本機獨立 SQLite 可使用：

```bash
python -m app.schema_init --sqlite /tmp/movingmatch-schema-review/app.db
```

此命令只建 Schema；不建立使用者、分館或配送資料。示範種子必須另外明確呼叫，且通過上述模式、路徑與空庫防護。

已提供 `--test-postgres` 入口，但本階段沒有執行。它只讀取專用測試連線變數，精確限制已指定的 Render 測試主機及 movingmatch_v194_test，拒絕其他 sslmode、service 與 hostaddr 覆寫，明確設定 verify-full 與 /etc/ssl/cert.pem；連線後再次檢查庫名及實際 sslmode。輸出錯誤不包含連線細節。未提供正式 PostgreSQL 初始化命令。

空庫順序為：目標驗證 → 基礎表（含 branches）→ V19.4 branch_signers → 其餘既有必要 Migration → 結構驗證與版本標記 → commit。無需複製正式庫。既有庫同樣使用完整交易，CREATE IF NOT EXISTS 不取代欄位驗證。此版本標記記錄整個 Schema 批次，不代表正式環境部署狀態。

執行：

既有 SQLite API、簽收、補簽、更正、權限、歷史、排程順延、報表及 Gmail mock 回歸一併執行。沒有以本機替身測試宣稱 PostgreSQL 真實交易或完整四角色瀏覽器驗收通過。

本次結果：75/75 PASS（既有 55 項，加上新增 20 項初始化安全測試）。其中雙程序測試實際啟動兩個獨立 Python 程序，競爭同一個全新暫存 SQLite；PostgreSQL 的兩項 SQL／交易控制測試僅使用替身。

仍待另行確認後驗證：PostgreSQL 18 真正空庫建表、既有庫 Migration、兩個獨立 PostgreSQL 程序的鎖等待、DDL 失敗實際 rollback、多連線交易隔離，以及原定 10 項 PostgreSQL 功能驗收。

## 相容性審閱事項

- 正式庫必須已具備必要 Schema；缺欄位時啟動會停止，不會自行 Migration。需先審閱實際版本，不應直接部署。
- 人工設定的名冊、啟用狀態及司機不再被重啟覆寫。新增／修復名冊、司機與 K13 身分需個別明確操作。
- 空庫只建 Schema 不足以登入；管理帳號與必要業務種子需獨立規劃，不可改用示範種子初始化正式環境。
- 每日重建保留既有配送，即使分館停用或排程改變。排程取消使用明確的既有作廢流程；不再靠看板讀取順帶刪資料。已存在但不應配送的舊待配送資料需人工核對。
- 本次不提供清空／重設功能。未來若新增，必須另行實作測試庫身分、測試模式、明確人工授權及資料批次所有權的共同防護。
